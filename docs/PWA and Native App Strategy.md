Livanta is a **mobile website** today. It is installable from the browser
(Add to Home Screen / install prompt), but it is not on the Play Store or the
App Store. This note records how we get there, and why in that order.

## Where we are

| | Status |
|---|---|
| Mobile web app | Live at the Cloudflare Workers URL |
| Installable PWA | Done — manifest, icons, service worker, offline shell |
| Play Store listing | Not started |
| App Store listing | Not started |

## The PWA layer

An installable PWA needs four things, all present:

1. **A manifest** — `app/manifest.ts`, served at `/manifest.webmanifest`. It
   declares the name, the standalone display mode, a root `scope` of `/` so
   every route is covered, and both `any` and `maskable` icons.
2. **Icons** — generated by `scripts/make-favicons.mjs` from
   `public/logo.jpeg`. Run that script after replacing the logo:
   `node scripts/make-favicons.mjs`
3. **A service worker** — `public/sw.js`, registered from
   `lib/serviceWorker.ts` at startup.
4. **Correct caching headers** — in `public/_headers`.

The manifest is generated through the Next Metadata API rather than placed in
`public/` on purpose: Next mangles filenames it does not recognise, so a static
`manifest.webmanifest` can be published as `manifest.webmanifest.txt` and then
rejected for having the wrong MIME type.

### Caching strategy

The service worker caches aggressively for build output and not at all for
everything else. That split is the whole design:

| Request | Strategy | Reason |
|---|---|---|
| Navigations | Network-first, cache as fallback | A stale HTML shell is worse than none |
| `/_next/static/*` | Cache-first | Content-hashed, so the bytes can never change |
| Icons, manifest | Cache-first | Unhashed but rarely change; a stale icon is invisible |
| Supabase and cross-origin | Never touched | Auth and sync responses must never be replayed |

`/sw.js` and `/manifest.webmanifest` are served `max-age=0, must-revalidate`
in `public/_headers`. This is not optional. A browser compares the bytes of a
cached service worker against its copy; if they match it keeps the old worker
and no update ever lands. Updates would appear to succeed and silently never
apply, which is the hardest PWA failure to notice.

### Bumping the cache

`CACHE_VERSION` in `public/sw.js` is the single lever. Bump it in any commit
that changes `app/layout.tsx`, `app/globals.css`, or the worker itself. The
`activate` handler deletes every cache that is not the current one, so a stale
shell cannot survive an update.

### Verifying it

```bash
npm run check:csp       # header delivery, enforcement, and clean render
npm run qa:responsive   # five viewports
npm test                # includes tests/pwa.test.tsx for the manifest and worker rules
```

`tests/pwa.test.tsx` asserts the things that break silently: that every manifest
icon exists **and is the size it claims** (read from the PNG header, not
trusted), that the worker ignores non-GET and cross-origin requests, that the
offline page loads no JavaScript, and that `_headers` never marks the worker or
manifest immutable.

To check offline behaviour by hand: build, then `npm start`, open
`http://localhost:3101`, load once, then switch the network off (DevTools →
Network → Offline) and reload. The app must still open with your data intact.

## Why offline support matters more here than in a typical PWA

Everything the user records lives in IndexedDB on their own device. There is no
server in the request path. So a dropped connection loses **nothing** — as long
as the app shell still loads. Without the service worker, going offline shows
the browser's error page while every bill and document sits right there in
storage, which reads to a user as data loss.

That is also the reason the offline fallback exists at `public/offline.html`:
it states plainly that saved data is still on the device, which is both true and
the single most reassuring thing to say in that moment. It carries its own CSS
and loads no JavaScript, so it works when the app's own bundle is exactly what
failed to load.

## Why not a TWA first

A Trusted Web Activity wraps the deployed URL and reaches both stores in about
a day, which is tempting. Two problems:

- **It ships a website.** Google Play rejects repackaged sites under
  *Repetitive Content*, and Apple's guideline 4.2 asks for features beyond a
  repackaged website. A TWA passes today and is fragile tomorrow.
- **It breaks with Access.** If Cloudflare Access ever covers that URL, the
  wrapper cannot authenticate and the app opens to a login page.

It also throws IndexedDB away on reinstall, which for this app is throwing away
the user's data.

## The Capacitor route

When reminders and document scanning are actually built, Capacitor is the right
step. It keeps the React app and wraps it in a native shell with a bridge,
which is what unlocks the features a PWA cannot reach:

- Native push notifications for bills and document expiry — the single biggest
  reason to go native, and not something a web push notification replaces well
- Camera-based document capture
- Biometric unlock
- Storage that survives reinstall, via Capacitor Preferences

Roughly a week of work, plus review time. Nothing in the current design blocks
it: the app is already a self-contained bundle with no server dependency.

Ordering matters. Building two shells before either has proven out is how you
end up maintaining a web app, a PWA and a native wrapper at once. The PWA gives
installability now at near-zero cost, and Capacitor still opens later without
rework.

### One migration to expect

IndexedDB does not carry across into a Capacitor WebView cleanly. Expect to
replace the storage calls in `lib/db.ts` with a Capacitor-backed adapter behind
the same interface, and to write a one-time import that moves existing records
over on first native launch. The `DB_NAME` and `DB_VERSION` constants and the
store layout should stay as they are, so the import is a read-and-write rather
than a conversion.
